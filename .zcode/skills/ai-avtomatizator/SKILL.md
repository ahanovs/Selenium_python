# AI-автоматизатор

## Источники истины

Перед изменениями:

1. Прочитай корневой `CODEX.md`.
2. Прочитай [PROJECT.md](PROJECT.md).
3. Изучи кейс `docs/test-cases/TC-NNN-*.md`, ближайший тест той же фичи
   и существующие файлы `pages/`.

Если пример в старом тесте расходится с `CODEX.md`, следуй `CODEX.md`.
Не копируй нарушение ради единообразия.

## Рабочий процесс

1. Уточни ожидаемое поведение из кейса. Задавай вопрос только если без ответа
   существенно меняется сценарий.
2. Найди переиспользуемые Page Object'ы и фикстуры до написания нового кода.
   Создай Page Object, если его ещё нет.
3. Открой страницу стенда в браузере (ZCode browser-use) и собери локаторы
   по реальному DOM. Приоритет: `data-testid` → `id` → роль/доступное имя → CSS;
   XPath — последнее средство. Не выдумывай локатор по исходникам и не копируй
   непроверенный из старого теста. Если приложение объективно недоступно — скажи
   прямо, какие локаторы не удалось подтвердить, не маскируй это догадкой.
4. Реализуй минимальный сценарий: тест не знает о разметке, страница действует —
   тест проверяет.
5. Прогони ruff и многократный прогон изменённых тестов (см. ниже). Красное — чини
   до полностью зелёного результата.

## Selenium-специфика

- Драйверы: Selenium Manager. webdriver-manager запрещён (AGENTS.md).
- Ожидания: только `WebDriverWait` + `expected_conditions`. `time.sleep` запрещён.
  Не миксуй implicit wait с явным.
- `shadow-dom-iframe`: XPath внутрь shadow root не работает в принципе.
  Открывай `element.shadow_root` (Selenium 4), внутри — CSS-локаторы.
- Headless: фикстура драйвера читает env `HEADLESS` (на CI = `1`).
- Стенд общий и учебный: ничего не сохраняем, cleanup аккаунтов не нужен;
  состояние страницы сбрасывай `driver.refresh()`.

## Структура теста

- Имя: `test_tcNNN_<поведение>`, docstring — ID кейса и формулировка (трассировка).
- Один проверяемый факт на тест; связанные проверки одного действия — в одном тесте.
- Каждый осмысленный этап оборачивай в `allure.step` с человеческим названием.
  В степе-действии — действия Selenium; в степе-проверке — только ассерты.
- Ассерты осмысленные, с сообщением-ожиданием. Без `assert True`.
- Page Object называет намерение (`submit_form`), а не жест (`click_button_2`).
- Ассерты из страницы не тащи. Допустимое исключение определяет `CODEX.md`.
- Повторившийся код выноси после второго использования.

## Защита от флаков

- Никаких `time.sleep`, force-действий и безусловных retry.
- Ожидай наблюдаемое состояние через `WebDriverWait` до ассерта.
- Не проверяй состояние, которое ещё не наступило.
- Десятикратный прогон нового или изменённого теста:

  ```bash
  python -m pytest tests/<файл> --count 10 -q
  ```

  Упал хотя бы один из десяти — найди причину и повтори все десять с начала.
  Не прячь нестабильность за retry или ослаблением ассерта.

## Дисциплина прогонов и правок

- **Один прогон за раз.** Перед запуском pytest проверь, что не живы старые
  процессы (python/pytest, chromedriver, headless chrome). Никогда не
  перезапускай прогон, не убедившись, что предыдущий умер, и не пиши два
  прогона в один лог — результаты смешиваются необратимо.
- **Правил кода → немедленный прогон.** Изменил тест или Page Object — сразу
  прогони затронутые тесты, до того как объявлять результат или звать ревью.
  Не накапливай пачку правок «с проверкой потом».
- **После структурных правок тестового файла** (добавление/перенос/удаление
  функций) собери `pytest --collect-only` и сверь количество и имена тестов —
  правка легко затирает объявление соседней функции.
- Selenium-грабли, проверенные прогонами: `move_to_element_with_offset`
  отсчитывает смещение от центра элемента; `EC.url_contains` смотрит URL
  текущего окна — сначала `switch_to.window`; JS-установка `value` обходит
  maxlength, `send_keys` — нет. Подробности в PROJECT.md ai-cheklistyor.

## API-специфика (уроки Блока 4, 2026-10-22)

- **Пробы и тесты ходят ОДНИМ HTTP-клиентом.** urllib молча подставляет
  `application/x-www-form-urlencoded`, requests — `text/plain` для строкового
  data: одно и то же «отсутствие заголовка» даёт разные коды (400 vs 415).
  Разведку делать тем же клиентом, что пойдёт в тесты, либо перепроверять
  сомнительные ветки клиентом тестов до написания ассертов.
- **Сомнительная ветка кейса — сначала проба, потом тест.** Если ассерт
  помечен «замер» или вызывает вопрос («а что стенд реально отдаст?»), не
  пиши тест по бумажке — прогони безопасную пробу и синхронизируй кейс.
  Три ошибки подряд в TC-050/054/055 были цепочкой одного рода: 403
  «Токен недействителен» приписали неверному паролю, а это был отозванный
  токен; «токен в теле обязателен» — тоже артефакт отозванного токена.
- **Не приписывай код ветке — приписывай его условию.** Замер верен только
  для полного состояния на момент замера (какой токен, какой пароль). Прежде
  чем записывать «замер» в кейс, проверь, что поменялось с предыдущим
  запросом (ротация токенов, смена пароля).
- **Скриптовые правки файлов — с немедленной проверкой.** После любого
  scripted-изменения .py — `python -m py_compile <файл>`; после .md —
  grep-сверка изменённых строк. Не реиндентируй код скриптом — переписывай
  файл целиком (реиндент-скрипт 2026-10-22 сломал все отступы разом).
- **Длинные генераторы — файлом, не heredoc'ом:** команда консоли обрезается
  по размеру; Write-файл + запуск надёжнее.

## Проверки перед публикацией

Сначала линт всего проекта:

```bash
python -m ruff check .
```

Затем десятикратный прогон затронутых тестов (см. выше). Если изменено несколько
тестов, прогоны должны охватить каждый.

Не объявляй работу готовой и не предлагай публикацию, пока линт и все прогоны
не зелёные. Не отключай правила ruff без явного запроса человека и технического
обоснования.

## Результат

Кратко перечисли изменённые файлы, подтверждённые по реальному DOM локаторы
и фактически выполненные прогоны (сколько раз, какой результат). Если проверка
не запускалась или стенд был недоступен, скажи об этом прямо и не утверждай,
что тест готов к pull request.
