# Карта проекта для чеклистёра

## Стандартные проверки (применять к любому блоку)

Эвристики тест-дизайна. Применять выборочно — не каждая проверка нужна
каждому элементу; отбор под конкретную систему делает автор.

**Текстовое поле:**
- первый тест — всегда положительный: корректное значение по бизнес-смыслу;
- буква «Ё» (не входит в `[А-Я]`);
- эмоджи (частая причина падений);
- спецсимволы с клавиатуры; разный регистр (КАПС, сТрАнНоеСлово);
- пустое поле и поле из одних пробелов (негатив «на ноль»; строка из пробелов
  может считаться пустой, если система их вырезает);
- пробелы до текста, после текста, между словами — как система обрабатывает;
- границы длины: нижняя, верхняя, технологическая.

**Технологическая граница:** «дальше-далеко» от бизнес-границыы — очень длинный
текст. Три правила: (1) многословный разумный текст, не одна буква —
односимвольная строка скрывает баги; (2) если с клавиатуры нельзя — вставка
из буфера или программная установка; (3) после вставки проверить, что система
жива, а не только что «всё работает в штатном режиме».

**Числовое поле:** корректные; некорректные (за диапазоном/нелогичные);
граничные и пограничные; дробное через запятую и через точку; округление
с кучей знаков; ноль; один; пустое; очень большое (техграница); отрицательное;
нечисловые и «не совсем числовые» значения («0x10», «1e5» — программа может
считать их числом).

**Поле с датой:** нормальная дата по целевой аудитории; нормальная, но
подозрительная для бизнес-логики (200 лет); дата из прошлого/будущего;
со временем и без; форматы — день и месяц не путать (ДД.ММ vs ММ.ДД);
логические границы; нереальные даты; ноль даты (00.00.0000, 01.01.1970);
дефолт (01.01.1900); технологическая (99.99.9999); максимум БД (9999-12-31);
ноль как строка; техграница строки.

**Форма:** первый тест — заполнить все поля и проверить результат; минимальный
набор (только обязательные); все поля пустыми (ошибка одна или все сразу?
адекватная ли?); каждое поле — по собственному чек-листу.

**Ссылки и вкладки:** внешняя ссылка — новая вкладка, доступность сайта в
предусловия; одна и та же форма в двух вкладках — параллельная работа ломает
системы, состояние независимое или общее?

**CRUDL (если в блоке есть сохранение/объекты):**
- Create: один объект; дубль; связанная сущность сразу; несколько параллельно
  (разные вкладки); под ролью без прав;
- Update: свежесозданный (0 правок) / отредактированный 1 раз / много раз;
  из разных исходных состояний; удалённый в соседней вкладке; правка меняет
  ДРУГОЙ объект — проверить этот другой объект;
- Delete: базовый; уже удалённый; изменивший состояние; изменивший связи;
  под разными ролями;
- List: все места, где объект отображается (общий список, поиск, карточка
  другого объекта) — про них забывают чаще всего;
- Live: другие действия и состояния (архивирование, копирование, откат...).

**Связи (если есть):** ноль/один/дубль/максимум; косвенное изменение и удаление
через связанные сущности.

**Ролевая модель:** действие под ролью с правами, без прав, гостем, админом;
роли отдельно и в сочетаниях (включая конфликтующие); запрет проверять в трёх
местах: кнопки в интерфейсе, прямая ссылка, API.

**Загрузка файлов (если есть):** тип (корректный / похожий по смыслу / совсем
не то); расширение; размер (внутри, границы, ноль); пустой файл.

**Модалки и состояния:** нарисовать схему состояний объекта — «стрелочки =
готовые кейсы»; проверять и невозможные переходы (Esc, закрытие без кнопок).

**Таблица решений:** условия — входные данные, действия — результат, колонки —
готовые тесты. Для параметризованных кейсов.

**Анализ тестов:** разделять тесты на функциональность и тесты на данные
(«10 000 платьев одного цвета проверять не надо»); схлопывать нельзя там, где
за тестами разная логика; порядок проработки: базовые → комплексные → «извращения».

**Pairwise:** применять, когда параметров много и значений в каждом мало
(1000 тестов → 10–20); более 80% ошибок сидит в парах; НЕ применять при 5+
параметрах по 5–10 значений — укрупнять классы эквивалентности (первое /
середина / последнее значение списка) или проверять попарно только связанные
параметры; минус — падение сложно локализовать.

**Исследовательские туры (методика Уиттакера) для новых блоков:** выбрать тур,
таймер (30–120 мин), идти строго по миссии, отчёт: какой тур и почему / что
покрыто / какие баги. Первые туры для нового блока: «путеводитель» (по
руководству пользователя) и «супермодель» (внешний вид и первое впечатление),
«деловой центр» (киллер-фичи).

**Эффект пестицида:** варьировать данные между прогонами, не гонять одну и ту
же строку.

## Как читать страницу

1. Открой `.../practice/<slug>` в браузере (ZCode browser-use).
2. Возьми DOM-снимок: роли, доступные имена, состояния элементов.
3. Проверь фактические `data-testid`, `id`, `aria-label` — только они идут в кейсы
   как основа будущих локаторов (сам локатор соберёт ai-avtomatizator).
4. Приём ревьюера (2026-10-09): клиентский код страницы доступен напрямую —
   JS-чанк `/_next/static/chunks/app/(public)/xpath-practice-hub/practice/<slug>/page-*.js`
   скачивается curl'ом (`curl --ssl-no-revoke`) и читается. Это фактическая
   логика страницы: шаги анимаций, тексты тостов, валидации, скрытые атрибуты
   (accept, multiple). Замер поведением + сверка с кодом — самый надёжный способ
   не ошибиться в формулировках.

## Грабли (проверено на живом стенде)

- Тестид — приоритет, но не гарантия: на autocomplete и context-menu их почти нет.
- Shadow DOM: XPath внутрь не работает — ни на этом стенде, ни в Selenium вообще.
- Из части окружений сайт недоступен напрямую (curl/SSL-ошибка), при этом в браузере
  открывается нормально — проверяй стенд через браузер, а не через HTTP-запросы.
- basic-elements, поведение (замер 2026-10-06): нет тега `<form>`, поэтому required /
  minlength / maxlength нативно не применяются; `maxlength=500` не ограничивает даже
  ввод с клавиатуры.
- basic-elements, тосты: рендерятся в собственном контейнере `fixed top-4 right-4
  z-50` без `role` и без `data-testid`; пустой `<ol>` от sonner рядом — ловушка;
  инлайн-алерт «Информационное сообщение» имеет `role=alert` и маскируется под тост.
- basic-elements: «Показать уведомление» — toggle (повторный клик снимает блок);
  тосты стекуются, автозакрытие ~3–4 c, кнопки закрытия нет ни у тостов, ни у
  модалки (только клик по фону), Esc модалку не закрывает; модалка без
  `role="dialog"` — локатор по классу/тексту, хрупко.
- basic-elements, модалка: в DOM ДВА div с классом `bg-black/60` — видимый
  оверлей с карточкой и невидимая копия у верха страницы, содержащая те же
  элементы (например, заголовок с `data-testid="modal-title"`); локаторы и
  клики — только внутри ВИДИМОГО оверлея (найденное первым совпадение
  перехватывается шапкой). Клик по фону должен попадать вне карточки
  (координатный клик по (200,500) закрывает); точка (30,30) — шапка/кнопка
  снежинок, а не фон. Esc не закрывает; кнопок закрытия нет.
- basic-elements, tab-порядок: между полями стоят кнопки «Показать локаторов» —
  Tab с поля попадает на них. Подписи связаны с полями через label: клик по
  тексту подписи переключает чекбокс.
