# Карта проекта для тест-кейсера

## Где что

- Кейсы: `docs/test-cases/TC-NNN-<slug>.md` — один кейс, один файл, slug латиницей.
- Чеклист: `docs/checklist.md` — источник пунктов; кейсы только по принятым пунктам.
- Карта стенда и замеры локаторов: [PROJECT.md чеклистёра](../ai-cheklistyor/PROJECT.md).

## Приоритеты

| Чеклист | Кейс | Смысл |
|---|---|---|
| P1 | High | сломанное закрывает фичу |
| P2 | Medium | заметный дефект, есть обход |
| P3 | Low | стоит проверить, не критично |

## Пример формата

Пример из шаблона человека — иллюстрация структуры, не кейс этого проекта:

```markdown
---
**ID:** TC001
**Название тест-кейса:** Проверка успешной авторизации с валидными данными
**Связанные требования:** US-101
**Предусловия:** Пользователь зарегистрирован в системе
**Шаги:**
1. Открыть страницу авторизации
2. Ввести валидный email
3. Ввести валидный пароль
4. Нажать кнопку "Войти"
**Ожидаемый результат:**
Пользователь успешно входит в систему и перенаправляется на главную страницу.
**Приоритет:** High
**Статус:** Not Executed
**Примечания:** Тестировать на десктопной версии сайта, Chrome 120+
---
```

Отличия в этом проекте:

- На стенде нет регистрации и авторизации — предусловия обычно «открыта страница X».
- В «Связанных требованиях» — пункт чеклиста (блок + формулировка), а не user story.
- Номерация кейсов: `TC-001`, `TC-002`, ... — этот же номер входит в имя будущего
  автотеста `test_tcNNN_<поведение>` (трассировка из CODEX.md).

## Грабли

- Не пиши в шагах локаторы и селекторы — кейс должен пережить смену разметки.
- Не пиши «проверить, что всё ок» — ожидаемый результат обязан быть наблюдаемым.
- Для негативных кейсов ожидаемое сообщение/поведение обязательно, иначе кейс
  непроверяем.
