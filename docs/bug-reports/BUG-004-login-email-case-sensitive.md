**ID:** BUG-004
**Заголовок:** Логин чувствителен к регистру email, при этом регистрация принимает любой регистр
**Severity:** Minor
**Priority:** Low
**Окружение:** Bro AI API `http://31.59.114.45:8000/api/v1` (Django REST Framework), замер 2026-10-22
**Воспроизводимость:** всегда
**Предусловия:** Нет (регистрация открыта).
**Шаги воспроизведения:**
1. `POST /api/v1/users/` с email `QA.USER.<штамп>@TEST.RU` (верхний регистр) → 201
2. `POST /api/v1/jwt/create/` с тем же значением, но в нижнем регистре: `qa.user.<штамп>@test.ru`

```bash
# 1. Регистрация в верхнем регистре
curl -sS -X POST "http://31.59.114.45:8000/api/v1/users/" \
  -H "Content-Type: application/json" \
  -d '{"username":"bugreport004","email":"QA.USER.2026@TEST.RU","password":"S3c!Reveal7Qz"}'
# → 201 {"username":"bugreport004","email":"QA.USER.2026@test.ru","id":42, ...}
#    домен нормализован в нижний регистр, локальная часть сохранена как введена

# 2. Логин в нижнем регистре
curl -sS -X POST "http://31.59.114.45:8000/api/v1/jwt/create/" \
  -H "Content-Type: application/json" \
  -d '{"email":"qa.user.2026@test.ru","password":"S3c!Reveal7Qz"}'
# → 401 {"detail":"No active account found with the given credentials"}
```
**Ожидаемый результат:**
Регистрация и логин регистронезависимы (email-адреса по стандарту нечувствительны к регистру домена и на практике — локальной части): логин в шаге 2 → 200.
**Фактический результат:**
Шаг 1 → 201; в ответе домен нормализован в нижний регистр (`@test.ru`), но локальная часть сохранена как введена (`QA.USER...`). Шаг 2 → 401 — пользователь, набравший email в другом регистре, в свой аккаунт не попадает.
**Дополнительно:**
Пробелы по краям email при регистрации молча отрезаются (нормализация), а дубликат проверяется по точному совпадению строки — смена регистра может позволить завести второй аккаунт на тот же ящик (не проверялось; кандидат в исследование).
**Доказательство:** автотест `test_tc044_special_input_facts` (tests/api/test_users_api.py); кейс TC-044.
