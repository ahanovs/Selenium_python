# Тест-кейсы XPath Practice Hub

> Блок 1 (basic-elements) — принят. Блок 2 (interactive-elements) — черновик,
> на ревью. Один кейс — один файл.
> Трассировка: `TC-NNN` ↔ `test_tcNNN_<поведение>` (CODEX.md, раздел 4).

## Правила набора

- **Кейс = будущий автотест.** Кейсы пишутся на основе чек-листа без 1:1: пункт
  может стать кейсом, частью кейса или остаться ручным ориентиром (маршруты —
  в чек-листе). Родственные проверки одного сценария объединяются в один кейс —
  в автотесте они станут одним параметризованным тестом.
- Приоритеты: **High = P1, Medium = P2, Low = P3**. У объединённых кейсов —
  наивысший из источников.
- Статус **«Only Automated»** — кейс выполняется только автотестом: ручной
  прогон невозможен или бессмыслен (пример: TC-021, чтение состояния за цикл
  200 мс).
- «Связанные требования» цитируют пункты чек-листа дословно.

## Вне рамок набора (12 пунктов чек-листа — явное решение)

Пункты остаются в чек-листе как ручные ориентиры и факты о стенде; кейсы на них
не заводятся. Пересмотреть при автоматизации соответствующих элементов:

1. Пустые поля показывают placeholder-подсказки (P2) — хрупкое сравнение строк.
2. Переключение радио без сброса остальных данных (P3) — частично покрывается TC-007.
3. Фокус перемещается по Tab (P3).
4. Несколько тостов подряд (P3) — наблюдается при прогоне TC-008.
5. Тост исчезает автоматически (P2) — тайминг флакоопасен; наблюдается при TC-008.
6. У тоста нет кнопки закрытия (P3) — фиксируется попутно в TC-008.
7. В модальном окне нет кнопок закрытия (P2) — фиксируется попутно в TC-011.
8. Esc не закрывает модалку (P3) — кандидат в кейс при автоматизации модалки.
9. Якорная ссылка (P3); кнопки-декорации без действий (P3).
10. Форма в двух вкладках — состояние независимо (P3) — кандидат в кейс.
11. Вставка из буфера обрезается maxlength до 500 (P3) — требует первичного замера.
12. `<script>` принимается как текст (P3) — кандидат в кейс по решению автора.

Граница «7 символов» (TC-014) — тот же факт, что и принятый кейс: валидация длины
пароля отсутствует без формы. «Ровно 500» (TC-015) — сама проверка maxlength.

## Заметки для автоматизатора (не часть кейсов)

- **TC-001**: шаг 4 «кликнуть на пустую область» реализован как Tab — клик по
  пустой области ненадёжен из-за сквозной геометрии страницы; Tab уводит фокус
  с того же инвариантом (грабли про tab-порядок — в PROJECT.md чеклистёра).

- **TC-003/TC-004**: список стран — кастомный dropdown (кнопка, не нативный `<select>`).
- **TC-004**: ожидание перерисовки после выбора — см. грабли PROJECT.md.
- **TC-008**: различение тостов по тексту; в DOM у тостов нет role/testid, контейнер
  `fixed top-4 right-4 z-50`, пустой `<ol>` от sonner — ловушка.
- **TC-009**: полный текст блока по замеру — «Это важное уведомление для пользователя.»;
  блок сам не исчезает (замер) — внести в чек-лист, если подтверждается при автоматизации.
- **TC-011**: полный текст карточки — «Модальное окно / Пример для автотестирования» (замер).
  В headless при высоте окна ~569px заголовок модалки перекрыт шапкой сайта — клик
  выполняется по центру карточки (тот же инвариант «клик внутри карточки не закрывает»).
- **TC-012**: в DOM два div с классом `bg-black/60` — видимый оверлей и невидимая копия
  у верха страницы (в ней свой `data-testid="modal-title"`); локаторы и клики — только
  внутри видимого оверлея. Selenium 4 отсчитывает смещение
  `move_to_element_with_offset` от центра элемента; рабочая точка фона — (200, 500)
  при вьюпорте 1280×1600 (фиксируется через CDP в фикстуре: на CI-раннере
  оконный размер ненадёжен, страница не прокручивалась — см. conftest).
- **TC-013**: поведение новой вкладки следует из `target=_blank`.
- **TC-015**: проверка `len(value) == 500` (maxlength обрезает ввод при наборе,
  замер 2026-10-07); программная установка значения через JS обходит maxlength —
  в тесте использовать только `send_keys`.
- **TC-016**: перезагрузка = чистое состояние — основа arrange для остальных тестов.
- **TC-017**: параметризованный тест «ввод → значение»; сравнение через
  `get_attribute("value")` — эмоджи и пробелы сохраняются в значении как есть.
- **TC-018**: установка 100 000 символов программно через JS-исполнитель
  (обход maxlength); проверка отклика страницы и отсутствия элементов с
  классом `error`; многословный текст, не одна буква.

### Заметки для автоматизатора (Блок 4)

- Базовый URL `http://31.59.114.45:8000/api/v1` — в фикстуру/конфик, не в тесты (заодно закрывает букву старого ДЗ «URL в фикстуру»).
- Фикстуры: `api_user` (регистрирует уникального пользователя, возвращает креды и токены; teardown — DELETE /me с current_password, идемпотентный: 401/403/400 — «убирать нечего»), `auth_headers`, свежая jwt-пара — три фикстуры ДЗ закрыты.
- Маркер `@pytest.mark.api`; allure-лейблы: epic/suite «API», feature «users», severity по приоритету кейса.
- Данные уникальны на прогон (timestamp в email и username). Пароли: не короче 8, не числовые, не похожие на username/email.
- Расхождения спеки с фактом (6) и находки — в примечаниях кейсов; сводка «Находки — кандидаты в баг-репорт» в чеклисте Блока 4.
- TC-057 — расходный аккаунт, уборка невозможна; TC-058 после logout требует свежий логин для уборки; TC-059 шлёт 7 запросов подряд — не параметризовать вверх без нужды.
- Критерий расщепления кейса на два теста: позитив (создаёт данные) и негатив (не создаёт) живут раздельно (TC-041, TC-051); ветки одного сценария с общим состоянием — один тест (TC-044, TC-047, TC-050, TC-054).
