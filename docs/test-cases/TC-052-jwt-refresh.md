**ID:** TC-052
**Название тест-кейса:** jwt/refresh: валидный refresh даёт рабочий access, мусор отклоняется
**Связанные требования:** Блок 4, пункты чек-листа: «jwt/refresh: валидный refresh → новый access, который работает на GET /me» + «jwt/refresh с мусорной строкой → 401»
**Предусловия:** Стенд Bro AI API доступен: http://31.59.114.45:8000/api/v1. Пользователь зарегистрирован; refresh из ответа (регистрации или jwt/create) в наличии.
**Шаги:**
1. POST /api/v1/jwt/refresh/ с телом {"refresh": <валидный refresh>}
2. Проверить код, получить новый access
3. GET /api/v1/users/me/ с новым access — проверить код
4. POST /api/v1/jwt/refresh/ с мусорной строкой — проверить код
**Ожидаемый результат:**
1–2) 200, в теле новый access. 3) 200 — новый access работает. 4) 401 с сообщением о невалидном токене.
**Приоритет:** Medium
**Статус:** Not Executed
**Примечания:** Замеры 2026-10-22. Бонус-замер: refresh МНОГОРАЗОВЫЙ — повторный refresh тем же токеном → 200, ротации и блэклиста нет; вместе с TC-055 складывается в тему «refresh-токены не инвалидируются». Поведение refresh ПОСЛЕ смены пароля — отдельный кейс TC-055.
