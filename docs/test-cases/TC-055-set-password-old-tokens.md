**ID:** TC-055
**Название тест-кейса:** НАХОДКА: после set_password старые access отозваны, но старый refresh продолжает работать
**Связанные требования:** Блок 4, пункты чек-листа: «После успешного set_password старые access-токены не выполняют действий → 403; НО старый refresh продолжает работать (см. „Находки“)»
**Предусловия:** Стенд Bro AI API доступен: http://31.59.114.45:8000/api/v1. Пользователь зарегистрирован; access и refresh, выданные ДО смены пароля, сохранены; пароль сменён через set_password.
**Шаги:**
1. GET /api/v1/users/me/ со СТАРЫМ access — проверить код и тело
2. DELETE /api/v1/users/me/ со СТАРЫМ access — проверить код (деструктивная операция с отозванным токеном)
3. POST /api/v1/jwt/refresh/ со СТАРЫМ refresh — проверить код
4. GET /api/v1/users/me/ с access, полученным в шаге 3 — проверить код
**Ожидаемый результат:**
1) 403 «Токен недействителен» — старый access отозван. 2) 403 — DELETE со старым access недоступен, аккаунт не удаляется. 3) 200 — старый refresh ПРИНИМАЕТСЯ и возвращает новый access. 4) 200 — этот access полноценно работает. Инвалидация после смены пароля неполная (кандидат в баг-репорт).
**Приоритет:** Medium
**Статус:** Not Executed
**Примечания:** Замеры 2026-10-22. Тест закрепляет фактическое поведение; при исправлении стенда ассерты пересматриваются. Уборка — по актуальному паролю.
